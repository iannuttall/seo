A cloud agent machine is rebuilt for each task, so nothing you set up by hand survives. Everything has to come from the agent's config, its start-up script and its secrets.

## Option 1: the hosted MCP

Add the server URL to the agent's MCP config, the same way as on your own machine:

```text
https://seoskill.dev/mcp
```

That URL is all the config needs. The MCP client keeps a token that points to your account. Whether that token survives a rebuilt machine depends on the client, so check your client's docs. The first sign-in also needs a browser. If your cloud agent cannot open one, use the CLI below.

Research keys saved on your [account page](https://seoskill.dev/account) work here too. Or send them from the agent's secrets as headers, for example `X-Ahrefs-Key`, so nothing is saved. The [API keys guide](/docs/keys) lists them.

## Option 2: the CLI with an account token

This is the simplest way to get everything, including Bing and crawls, on a machine with no browser. On your [account page](https://seoskill.dev/account), under **Linked machines**, choose **Make a token for a cloud agent** and save it in the platform's secrets as `SEO_TOKEN`. Then install the CLI in the start-up script:

```sh
npm i -g seo
```

The CLI uses your account's Google accounts, Bing and keys, with nothing else to set up. Remove the token on the account page when you no longer need it.

If the agent can show you a link, it can also run `npx -y seo login` and ask you to approve the machine. That link lasts only as long as the machine, so a token is better for machines that are rebuilt.

## Option 3: the CLI with a Google service account

The CLI can also run with no account at all. It needs three things from the platform: an install step, a Google service account, and your keys as secrets.

### Create a Google service account

1. In Google Cloud, create a service account and download a JSON key for it.
2. In Search Console, open each property's settings, then **Users and permissions**, and add the service account's email address as a user.
3. If you want Google Analytics too, add the same email as a Viewer on the Google Analytics property.

The service account reads Search Console and Google Analytics with read-only access, like a normal sign-in.

### Add the secrets

Store these as secrets in the platform, so they arrive as environment variables:

| Variable | What it holds |
| --- | --- |
| `SEO_GOOGLE_SERVICE_ACCOUNT_JSON` | The whole service account JSON key |
| `SEO_DATAFORSEO_LOGIN`, `SEO_DATAFORSEO_PASSWORD` | Optional, for research with DataForSEO |
| `SEO_AHREFS_API_KEY` | Optional, for research with Ahrefs |
| `SEO_BING_API_KEY` | Optional, for [Bing Webmaster Tools](/docs/bing) data |
| `SEO_CLICKY_SITEKEY` | Optional, read by the [Clicky provider package](https://github.com/iannuttall/seoskill-clicky-provider) |
| `DO_NOT_TRACK` | Optional. Set to `1` to turn off the [anonymous usage counts](/telemetry) |

If the platform gives you a file instead, set `SEO_GOOGLE_SERVICE_ACCOUNT_FILE` (or `GOOGLE_APPLICATION_CREDENTIALS`) to its path. Set only one of the three Google variables.

### Install in the start-up script

```sh
npm i -g seo
```

If your platform has a persistent volume, point the CLI's state at it so keys and caches survive between runs:

```sh
export SEO_CONFIG_DIR=/workspace/.seo/config
export SEO_CACHE_DIR=/workspace/.seo/cache
```

Commands take the site directly, so there is no setup step to run:

```sh
seo report --site example.com --json
```

### Give the agent a clear prompt

```text
Use the seo CLI. Run seo report --site example.com --json, then the
quick-wins section. Summarise the facts and list the pages to look at.
Never print environment variables, keys or the service account JSON.
```

## Keep keys out of logs

Never print a key, paste one into a prompt or commit it to the repository. Put keys in the platform's secret store only, and do not echo environment variables in the start-up script. Anonymous usage counts turn off by themselves in common CI environments.
