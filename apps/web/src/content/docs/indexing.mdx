Search Console emails you about indexing reasons such as "Page with redirect" or "Blocked due to unauthorized request (401)". Many of them need nothing from you. `seo index` shows which ones do.

## Check your indexing reasons

Ask your agent:

```text
Why are some pages on example.com not indexed, and which ones need fixing?
```

The hosted MCP runs `seo_index`. In a terminal, run:

```sh
seo index --site example.com
```

`--site` takes a domain, a URL or a Search Console property.

## What comes back

Search Console's Page indexing report has no API, so `seo index` asks Google about pages one at a time. It takes the pages it knows about (pages that lost clicks, the home page, your sitemap, then pages with Search Console impressions) and checks up to 100 of them on each run. It always says how many it checked out of how many it knows, and whether it stopped at 100 or at Google's daily limit. A page it did not check has no result, so a short run is never an all-clear.

For each page you get Google's reason, word for word, then what the page does now: its status, where it redirects and whether that redirect is permanent, the canonical the page declares and the one Google chose, the pages Google saw linking to it, whether your sitemap lists it, and when Google last crawled it.

Each page also gets one of four labels, with the reason for it:

| Label | What it means | Examples |
|---|---|---|
| fix | The evidence shows a fault on the site | A temporary redirect on the same site, a missing page your sitemap or your own pages still link to, a sitemap page Google will not index |
| check | A person should look | "Crawled - currently not indexed", "Discovered - currently not indexed", Google choosing a different canonical, a noindex Google saw that the page no longer has |
| expected | The site works as built | An http:// page that permanently redirects to the https:// page, a sign-in page that answers 401 |
| indexed | Google indexes it and nothing looks wrong | |

The labels come from simple rules over this evidence, not from Google. Where a rule guesses (a 403 on a path that looks like a sign-in area, for example) the result says so.

The live check sees what your server sends. A browser can show "307 Internal Redirect" for an http:// page because it remembers your site uses https; that hop never reaches the server, so it never shows here.

## Run it each week

Run it once to get a baseline and keep the full result:

```sh
seo index --site example.com --detail full
```

Then run it again each week and compare the two by page and reason. A new reason, or a page that moved to fix, is the thing to look at. `seo` keeps no history, so your agent stores each week's result (a scheduled agent task is ideal for this).

Once your agent runs this every week, you can turn off Search Console's indexing emails. For one page from an email you already have, use [`seo page`](/docs/page).

## Pages that lost their clicks

The same result starts with pages that had at least 3 clicks in the previous 28 days and kept 20% or less of them in the last 28 days. Add `--start-date` and `--end-date` to change that window. A page that lost clicks but looks fine on both checks may have lost rankings rather than broken, so look at its queries with [`seo page`](/docs/page).
